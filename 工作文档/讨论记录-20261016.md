## 1 本场推翻的**产品假设**（用户当场拍的话）

| 假设 | 结论 |
|---|---|
| 画台要商用、要卖 | ❌ **推翻**。用户 2026-10-16 明确："**不再考虑这个项目的商用性**" |
| 理由（用户给的三条） | ① 现在**复刻容易**（别人能很快做出来）；② **AI 破解容易**；③ **说不定也开源**（但用户自评"水平低，开源有点班门弄斧"） |

**⇒ 连带结论：GPL 那条边界不再是"红线"，但仍不进版本库。**

- 商用性取消后，**GPL-3.0 的法律压力大幅下降**（不分发就不触发传染）；
- **但本场仍决定：一律不把 GPL 代码/文本搬进版本库。** 理由有三：
  1. 用户"说不定也开源"——**门没关死**，留着不堵；
  2. 跨栈移植成本本身就极高（见 §4），借代码不划算；
  3. **真正的风险在"模型许可证"**（见下），那条跟商用与否无关、跟分发有关，仍然必须查。

### ★ 顺带查实一个此前没查过的雷：**代码许可证 ≠ 模型许可证**

**实锤**（读 `参考代码\ai-art-engine-main` 的文档得出，它自己标了风险）：

| 组件 | 许可证 | 能否随包分发 |
|---|---|---|
| **YOLO11 / YOLOv8 官方权重**（最常用的实例分割） | **AGPL-3.0** | ⚠️ **有传染风险**；它文档原话是"商用前请评估或替换" |
| MobileSAM / SAM | Apache-2.0 | ✅ 可以 |
| MediaPipe FaceMesh（人脸 468 点） | Apache-2.0 | ✅ 可以 |
| BiRefNet（抠像） | MIT | ✅ 可以 |
| Real-ESRGAN | BSD-3-Clause | ✅ 可以 |
| InsightFace / RMBG-2.0 / CodeFormer | 研究许可 / CC-BY-NC / 非商用 | ❌ 不可以 |

**⇒ 本场定一条自查纪律（建议进决策记录）：凡要引入任何第三方代码/模型，先查许可证，查不到明确宽松许可的一律不引入。**

## 2 两份参考的定性结论（第一件任务的产出）

### 2.1 `artcraft`（Tauri + Rust + React/Three.js，类 PS + 3D，62 个云端生成模型）

**用户判断得到印证**：它是**开源的手工绘图替代**（2D 画布 + 3D 场景 + 多轨剪辑），AI 部分是**把手工标记接到云端生成模型**。

| 问 | 答（**实锤**） |
|---|---|
| 它怎么"精确选区"？ | **纯手涂笔刷**（Mask 工具，Add/Erase 两态）。**没有魔棒、没有套索、没有 SAM、没有任何自动选区** |
| 掩码格式 | 用户涂的笔画层 → PNG → 逐像素按 **alpha==0 涂黑（不改），否则涂白（改）** |
| 它有没有"动手前给用户看那块"？ | **没有**。生成按钮只 gate"底图加载完没有"，**不 gate"涂了没有"**（空蒙版也能提交） |
| 选区能不能事后改？ | **不能**（蒙版层 `listening=false`，选中不了/移不动） |
| 它有没有 AI 助手？ | **没有**。全仓库 163 处 `agent` 命中**全是 HTTP 的 `User-Agent`**；没有 agent、没有 MCP、没有 LLM 调用、没有 prompt 增强；Rust 侧**无任何 LLM 依赖** |
| 它的"AI 辅助"是什么？ | ① 蒙版重绘（手涂蒙版 + 一句话 → 远端模型，只改白区）；② 整图快照编辑（把标记烧进像素上传）；③ 一个 `enable_system_prompt` 布尔值，发给**它自己的服务端** |

**★ 最有价值的是这条负面证据**：
> 一个成熟的、商业化的、接了 62 个模型的 AI 图像工具，**在"精确选区"上选择了"让用户自己涂"**，而不是做语义理解。

**⇒ 推论（推断）**：它面向专业美术，美术愿意涂，所以绕过是合理的商业选择；**我们的用户是"不懂工艺的普通人"，这条不能绕。我们啃的是别人有意绕开的硬骨头。**

**许可证**：**MIT / Apache-2.0 双许可**（宽松，可商用）。可惜**它在精确选区上没东西可抄**。

### 2.2 `ai-art-engine`（Electron + Vue3 + TS，GPL-3.0，Agent 原生的美术资产引擎）

**它才是"精确选区"这条线上真正对口的参考**（用户后补说明：这是刚看到的开源，感觉思路相近）。

**★ 核心实锤一：它内置的就是我们用的那个 DSH。**

出处：`参考代码\ai-art-engine-main\src\main\services\deepseekHarnessService.ts` 头部注释与配置代码。

```
Chat 面板 → HARNESS_RUN → 常驻 dsh worker（stdin NDJSON prompt）
  → dsh 内嵌 mcp-client → http://127.0.0.1:<port>/mcp (Bearer token)
  → 工具执行 → MCP 活动广播给渲染层做工具卡
dsh stdout/stderr 按行转发为 HARNESS_EVENT（assistant / status / done / error）
```

- 包名与门槛都写在代码里：`@deepseek-ai/dsh`、Node **≥ 22.19**（用 Electron 内置 Node，`ELECTRON_RUN_AS_NODE=1`）；
- 它知道我们踩过的同一个坑：**`persona` → `personaPrefix` 在 0.1.5 改名**；
- 它**自写 runner 覆盖官方 headless runner**，**自写 approval 应答器**把 dsh 的审批接到自己的界面，**接管 system-prompt 注入自己的人格**；
- 它把应用内的专业流程渲染成 **`SKILL.md` 快照进 `$DSH_HOME/skills`**，于是 agent 自动"会"这些技能；
- 它踩了三个**只有"把 dsh 嵌进自己的 GUI 应用"才会踩**的坑，都打了补丁：
  1. **dsh 在 Windows spawn 子进程不传 `windowsHide` ⇒ GUI 宿主里弹黑窗**；
  2. agent 会**自己去起浏览器**（`--headless --screenshot`）想"看"东西；
  3. ACL 沙箱在 Windows 会**新建可见控制台**。

**★ 核心实锤二：它的精确选区，靠的是"本地 ONNX 视觉栈 + 点一下"。**

| 动作 | 行为 |
|---|---|
| **左键点一下** | 跑本地实例分割 → 取**外接框包含该点、且像素掩码也覆盖该点**的实例中**最小的那个** |
| **点空了** | 界面上**明说**"这里没有识别到可选目标，换「框选」拖一个框试试" |
| **拖一个框** | 直接出矩形掩码，**不依赖任何模型** |
| 选中后 | 按**长边 1.2% 膨胀**（理由原话：贴轮廓切会在边缘留原主体残影）+ 羽化 + **去边缘光晕** |
| 保护已改区 | 目标掩码**减去**已改好的区域，并报告重叠率 |
| 姿态 | 点选/框选 → 黑白掩码 PNG（白=改） |

底层：`onnxruntime-node` + `utilityProcess.fork()` 独立进程（崩了不拖垮主程序），**纯 CPU、离线、零调用成本**。

**★ 核心实锤三：它明确认定"视觉模型不能拿来出像素掩码"。**

它的实体识别走多模态大模型，但代码里把输出标成 `pixelEditable: false`，注释原话是：**视觉模型不给框/掩码，不能声称可做像素级替换**。

**⇒ 这与我们上一场的结论完全一致，而且给出了分工边界：VLM 只做"认得出、点到名"，掩码另外用几何手段拿。**

**⚠️ 两个"它其实没做完"（防止我们误以为有现成可抄）**：

| 事实 | 证据 |
|---|---|
| **SAM 2.1 只有"模型管理"（下载/扫描/校验体积），没有推理**。代码注释自承"仓库里没有 SAM2 推理" | `yoloService.ts` 只有 `scanSam2Models()` |
| **跨帧传播是死代码**（全仓库只有定义、无任何调用方），且其内部走的是 YOLO 分割而非 SAM | `sam2Propagate.ts` |

**★ 它还留了一条"眉毛级"的施工图**（v1 做过 468 点语义稠密环：脸缘/额头/左右眼/左右眉/鼻/内外唇/牙齿；v2 因为改用图片模型**整条删掉**，但在文档里把**重建口径和几何自检**完整留档了）。这条对"两个眉毛都改"**正是需要的**。

**⚠️ 它自己踩的坑（对我们是直接警示）**：用 `tflite2onnx` 转 MediaPipe 量化权重，**图形状全对但量纲整体偏小、人脸框缩到 1/4、置信度 0.81→0.67，而且不报错**。它自己的定性：这是"五官/妆容**静默失效**"的典型来源。
**⇒ 将来自己转模型，必须做数值对拍。**

**许可证**：**GPL-3.0**。⇒ **只读思路，不搬代码，不搬文本。**

## 3 五个场景的**同构**：卡点归纳

> ⚠️ **口径提示（2026-10-16 晚补）**：本节是参谋长在用户收窄范围**之前**做的归纳，用途是**证明"这些场景是同一个问题"**。
> 用户随后明确：**视频助手是随口一说，移出框架**（见 §6.5）；实战只做**玻璃画 + 剪纸画**两个领域，
> 犀牛鞋垫是**同一框架的第二个领域实例**（不是现在的任务）。**故 §3 / §5 的"五个场景"是分析范围，不是排期范围。**

**实锤/推断标注**：下面是**推断**（基于用户描述与已有实测归纳），不是新实测。

用户原话："这两个项目都卡在**自然语言交互、数据提供的准确性**。"

翻译成工程语言：

> **卡的不是"让 AI 变聪明"，是"让 AI 说的每个数，落到执行层时还是对的"。**

| 场景 | 用户会说的话 | 最容易错的一步 | 错了的代价 |
|---|---|---|---|
| 玻璃画 | "眉毛太密，两个都改" | 哪块像素 + 改多少 | **86% 的改动漏到圈外**（已实测） |
| 鞋垫 | "足弓有点顶脚" | 降几 mm、降哪儿 | 脚感不对、废料 |
| 剪纸 | "五官别掉下来" | 哪块是孤岛、桥接多宽 | **切出来是废品** |
| 犀牛 | "稍微高一点" | "稍微"= 多少 mm | 模型不可打印 |
| 视频 | "做成 15 秒广告" | 时长/风格/成本 | **花钱重做** |

**共同形状：模型每一句听起来都对，但落不到一个可验证的数上。所以框架要解决的不是"理解力"，是"对账"。**

## 4 框架草案：**三层 + 四道协议 + 一条核心赌注**（★ 待用户确认）

### 4.1 骨架

```
        用户一句话（自然语言，天然模糊）
                 │
     ┌───────────▼────────────┐
     │  ① 词汇层  lexicon      │  ← 唯一真源，与执行层同源，禁止手写第二份
     └───────────┬────────────┘
                 │  协议A：LLM 只许「挑」，不许「编」
     ┌───────────▼────────────┐
     │  ② 意图层  intent       │  ← LLM 在这里，只输出结构化 JSON
     └───────────┬────────────┘
                 │  协议B：参数必须过校验器，过不了整轮作废
     ┌───────────▼────────────┐
     │  ③ 执行层  executor     │  ← 确定性代码，不含 LLM
     └───────────┬────────────┘
                 │  协议C：独立回读（不许自证）
     ┌───────────▼────────────┐
     │  ④ 验证层  verify       │  ← 从产物反算事实，对不上就报错
     └───────────┬────────────┘
                 │  协议D：账（只追加、三分、只进不改）
     ┌───────────▼────────────┐
     │  ⑤ 账层    ledger       │  ← 人和机器的话不混行
     └────────────────────────┘
```

**注：这套骨架不是新编的，是从画台现有代码抽出来的**（词汇层=位置词表；意图层=一轮对话；执行层=确定性管线；验证层=从 BMP 反算；账层=流水三分）。

### 4.2 ★ 核心赌注（框架最重要的一条）

> **绝不让 LLM 产出"数"，只让它产出"选"。**

- ❌ 不让 LLM 输出坐标；
- ✅ 让它从**封闭词表**里挑一个词，**由代码算出像素/毫米**。

**理由**：LLM 生成一个数，**我们无法验证它对不对**；LLM 从一个**有限的清单**里挑，**我们 100% 能验证它在不在清单里**。
**⇒ "数据准确性"不靠让模型更准，靠把"生成"改成"选择"。**

### 4.3 五个场景的**共用与不共用**

| 层 | 五个场景 | 能否共用 |
|---|---|---|
| ① 词汇层 | 各自不同（"左边一列" / "足弓峰值" / "15 秒竖屏"） | 结构共用，内容各自 |
| ② 意图层 | 几乎一样（理解 + 反问 + 校验 JSON） | ✅ **共用** |
| ③ 执行层 | **彻底不同**（灰度管线 / 矢量化 / Grasshopper / 模型 API） | ❌ **插槽** |
| ④ 验证口径 | **彻底不同**（墨点占比 / 孤岛数=0 / 最小壁厚 / 成本） | ❌ **手艺所在** |
| ⑤ 账层 | 结构一样 | ✅ **共用** |

**⇒ 能合并的是"骨架"，不能合并的是"手艺"。**

### 4.4 ★ 协议零：基座与真源的边界（由用户本场的洞察引出）

用户本场的判断原话精神：**"现在讨论 dsh 最多的是它自身的能力和插件，都忽略了 dsh 最大的能力——用它做基座，去做适合自己 agent 的项目。"**

**这个判断被采纳，并落成框架的"协议零"：**

> **dsh 负责"听懂和翻译"；宿主负责"算准和兑现"。**
>
> | dsh 提供的（基座） | 我们必须自己提供的（真源 + 手艺） |
> |---|---|
> | agent 循环 | **词汇层**（唯一真源，与执行层同源） |
> | 工具 / 技能注册机制 | **校验器**（过不了整轮作废） |
> | 会话与上下文 | **执行器**（确定性代码，不含 LLM） |
> | 审批与沙箱边界 | **独立回读**（不许自证） |
> | 流式与插件装配 | **账**（只追加、三分） |
>
> **允许交给 dsh 的**：工具注册、技能发现、会话、人格、输出流、审批 —— **全部可以接管**。
> **永不允许交给 dsh 的**：**"什么是对的"**（校验器、回读口径、工艺约束、能力清单）。

**★ 配套判据（提议）："换掉 dsh 测试"**

> **把 dsh 整个换掉，我们的东西还对不对？**
> 换掉后依然成立的部分 = **我们的资产**；跟着 dsh 一起没了的 = **我们只是在配插件**。

### 4.5 ai-art-engine 的"基座接管清单"（当参考用，附出处，不抄代码）

它把这五层**全都接管了**，我们只接管了两层：

| dsh 的可接管面 | ai-art-engine | 画台（现状） |
|---|---|---|
| **模型/协议** | ✅ 接管（它实测发现 `DSH_MODEL` 环境变量**不生效**，必须写 settings 的 `agent-default-model`） | ⚠️ 部分（key 走环境变量，模型用默认） |
| **能力面（工具）** | ✅ 全接管（自写 MCP 服务，把 67 MB 能力注册成工具） | ❌ 没接管（**故意不给工具**） |
| **技能面（skills）** | ✅ 全接管（GraphSkill → `SKILL.md` 快照） | ❌ 没接管（改用提示词里塞能力清单） |
| **人格面（system-prompt）** | ✅ 接管（`personaPrefix`） | ⚠️ 部分（提示词里写纪律） |
| **输出面（runner）** | ✅ 接管（自写 runner 以吐思考过程） | ❌ 没接管（吃默认输出） |
| **安全面（approval + 沙箱）** | ✅ 接管（审批转发到 UI） | ❌ 不需要（不给工具，agent 碰不到系统） |

**★ 本场的自我发现**：**"拿 dsh 当基座"这件事，我们其实已经在做，只是没意识到。**
**证据（实锤，上一场记录）**：`sdk-minimal` profile 报"没有附件仓库"，升到完整 `sdk` profile 后图片才真的存下来。
⇒ **dsh 不是"装上就能用"的成品，是一堆可装配的零件；"完整能力"要靠自己在 profile 里装配出来。** 这就是"基座"问题的第一个实例。

**⚠️ 三个 Windows 补丁是"基座化"的入场费**（我们现在没交，是因为还没让 agent 动手）：
1. spawn 子进程弹黑窗 —— **我们的 exe 也是 GUI，迟早撞**；
2. agent 自己起浏览器 —— **一旦给 agent 工具就会撞**；
3. 沙箱新建可见控制台 —— 同上。

## 5 五个场景的**关系**：能不能合并（本场结论）

> ⚠️ 同 §3 的口径提示：此处的"五个场景"是**分析范围**；**排期范围是玻璃画 + 剪纸画**（视频已移出，鞋垫是下一个领域实例）。

**用户的问题**："我也不知道是否可以把这几个项目合并到一起。"

**结论（三段式）：**

| 层次 | 结论 | 理由 |
|---|---|---|
| **框架层**（词汇/意图/校验/回读/账） | ✅ **能合并，而且必须合并** | 骨架与领域无关；画台已验证 |
| **产品层**（五个助手） | ❌ **不能合并** | 用户不同、危险不同、验证口径不同、词表不同。硬凑会得到"什么都能干、哪个都不好用" |
| **沉淀层**（词典 + 账 + 手艺） | ⚠️ **真正要合并的是这一层** | 见下 |

### ★ 沉淀层 = 用户要的"人机共同成长"

| 沉淀什么 | 例子 | 为什么值钱 |
|---|---|---|
| **词典** | "顶脚"= 足弓峰值 −2mm；"有点密"= 墨点 −3 个百分点 | **同一句话以后永远翻译成一个意思** |
| **账** | 谁改的、从多少到多少、结果如何 | 用户原话目标："**免得使用者和 LLM 重复犯错误**" |
| **手艺** | "TPU 85A 前掌 <2.5mm 必踩穿" | 失败案例固化成**断言**，不靠 LLM 记 |

### ★ 一条从鞋垫项目继承过来的框架级铁律（同构适用）

用户此前在鞋垫项目上的判断（记录于 `参考代码\对话全文记录_3D打印TPU鞋垫与AI协同系统.md`）：

> **给模型加"语义标注/特征锚点"，然后引用标注交互**，而不是让用户在犀牛里手动拉扯。
> 理由：手动改会**打碎参数化逻辑链**，大模型无法从几万个顶点反推原始数学变量。

**⇒ 推断：这条在玻璃画上完全同构** —— 用户圈的"那块"，就是玻璃画里的"特征锚点"。
**⇒ 建议提为框架级铁律：引用"锚点/名字"，而不是描述"坐标"。**

## 6 ★ 用户的真实目标与"人机共同成长"的落地机制（2026-10-16 用户答）

### 6.1 用户的目标原话（本场最重要）

> **"我做玻璃画、剪纸画助手的目的，就是想让比我更不懂电脑的朋友，去制作可以雕刻的玻璃画和剪纸画。"**

**⇒ 这把铁律升级了（推断，待确认）：**

| 原来的铁律（决策 #23） | 升级后 |
|---|---|
| 不许要求用户**先学一套符号**（不数格子、不记编号） | **不许要求用户先学任何东西 —— 包括学这个软件本身** |

**配套硬约束（建议进框架）：**

> **允许的操作面（A 面）—— 用户只需要会：**
> ① 给一张照片；② 说人话；③ **用鼠标圈一块**（且这是**上限**，不是起点）
>
> **禁止的操作面（B 面）—— 永远不许要求用户：**
> 装配置、填路径、选目录、选格式；理解 dpi / mm / 墨点占比 / 上机档 / BMP；记编号、数格子、挑菜单项、学符号；**看任何参数**

**可判定的判据（提议）：任何一个界面元素，问"我朋友看不懂电脑，他能用吗？"答不能 ⇒ 不许出现在界面上。**

**★ 另一条推论：既然朋友听不懂"墨点占比/dpi/上机档"，这些词就不该出现在界面上 —— 只该出现在账里（供排查）。**
用户看到的永远应该是"这张脸会偏黑一点，要不要我提亮？"这种话。

### 6.2 "人机共同成长" = 两张表，一套机制

用户明确："人机共同成长**对，这个就是我一直想实现的**"，并分为两点：

| | **第一点：领域** | **第二点：个人** |
|---|---|---|
| 用户原话 | "助手越来越熟悉他干的工作，比如玻璃画、剪纸画这个领域" | "以后的鞋垫助手……也更熟悉某个人的脚和走路习惯" |
| 建模为 | **领域经验** | **个人档案** |
| 归属 / 共享 | 领域内**共享**（用户与朋友共用） | 只属于**那一个人** |
| 隐私 | 无所谓 | ⚠️ **有**（身体数据） |
| 生命周期 | **永久**，越用越厚 | 跟人走；人不用了即冻结 |

**★ 架构判断（推断）：不做两套系统，做一套"带作用域的账"。**

```text
一张「经验账」 = { 作用域(领域 | 个人), 用户原话, 当时参数, 做了什么, 结果如何 }
  作用域 = 玻璃画   → 领域经验（"这张脸墨点超过 28% 就糊了"）
  作用域 = 朋友A    → 个人档案（"A 习惯脸雕浅一点"）
```

**★ 但两者"怎么进账"必须不同（关键，建议进决策）：**

| | 怎么沉淀 | 要不要用户过一道手 |
|---|---|---|
| **领域经验** | 失败案例 → **提炼成规则** → **用户确认后**才进账 | ✅ **必须**（这是手艺，错了害所有人） |
| **个人档案** | 用一次**自动累积** | ❌ 不用（这是习惯，自动学即可） |

**理由：领域规则一旦自己悄悄长出来，就变成"没人知道为什么的约束"，将来出问题查不出来；个人偏好错了代价小。**
**呼应已有纪律**：决策 #10（不许手写第二份）、#14（缺口必须显式上报）——同一种"不许静默"的精神。

### 6.3 产品形态（用户答）

> 用户原话精神：**自用；随便找个电脑，拷贝过去，填写 API key，让朋友自己捯饬**；
> 朋友需要会三件事：**自己捯饬 / 聊天 / 用鼠标圈选某个范围**。

**由此带出的三个实情（需用户知晓）：**

| # | 实情 | 影响 |
|---|---|---|
| 1 | **朋友花的是用户的额度** | 填的是用户的 DeepSeek key；人多或乱聊会烧钱；将来要么各填各的，要么要能看用量 |
| 2 | **"随便找个电脑"会撞已踩过的坑** | 整套必须在**工作区外**才能跑（工作区里 exe 是 Low 完整性 ⇒ WebView2 崩）。朋友电脑上没有"DSH 工作区"概念，此坑**可能不出现**，**但也可能以别的形式出现 ⇒ 未验** |
| 3 | **"填 API key"对不懂电脑的人就是一道墙** | 需要账号、充值、找 key、复制粘贴。**建议：配的那一步由参谋长/用户代做，别让朋友自己配** |

### 6.4 ★ 新发现的**前置卡点**（比"眉毛"更靠前，未解决）

完整链条里有一格是空的：

```
朋友有照片 → 画台 → 出 BMP → ??? → 激光机雕出来 → 玻璃画
                                ↑ 这一格是空的
```

**激光机不是插上就雕的，中间有一个"上机软件"**（LightBurn / RDWorks / 各家自带），朋友要在里面：
打开 BMP、**设功率/速度/行距（激光参数！）**、对位聚焦、点开始。

**⇒ 怀疑这才是真正的卡点。** 待用户回答：
- 若**朋友自己雕** ⇒ "上机参数"也得进框架，且又是一次"不能让他看见参数"的难题；
- 若**用户自己雕** ⇒ 产品边界停在"出 BMP"，**范围小很多**，可专心做透"改哪儿"。

**这个问题会决定框架边界，优先级高于视觉 key。**

### 6.5 AI 视频助手：**移出本框架**（用户 2026-10-16 明确）

用户原话："视频助手我只是随口一说，我自己还一点知识都没有呢。"

**⇒ 结论：暂不纳入框架。** 理由：它的执行层是**云端模型**（要花钱、结果不可复现），
与玻璃画/剪纸画"确定性 + 可复现 + 免费"的骨架是两种东西，硬塞进来会让框架变糊。
将来若真要做，**单独开一个框架实例**，不改动本框架。

**⇒ 框架范围由此收窄为两个领域：玻璃画、剪纸画。**（鞋垫是同框架的第二个领域实例，见 §6.2）

## 9 一句话小结（本场）

> **dsh 是基座，但"什么是对的"必须留在我们手里。**
> 骨架共用（词汇→意图→校验→执行→回读→账），**"验证口径"就是各自的护城河**；
> **领域经验要用户点头才进账，个人档案自动累积**——这就是"人机共同成长"的落地形式。
> ai-art-engine 是**正面参考**（示范基座能接管到多深）兼**反面教材**（它把"什么是对的"交给了模型，所以做不到"眉毛太密，两个都改"）。
>
> **实战范围（用户 2026-10-16 定）：玻璃画 + 剪纸画两个领域；用户 = 用户本人 + 比他更不懂电脑的朋友。**
