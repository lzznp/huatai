## 1 ★★ 把"画台接上 agent"补全（工具化）

### 【想要什么】

让 agent 能**真正动手**做画台里已有的操作，而不只是"翻成人话"。

**具体分两块，量级完全不同，别混着看：**

| 块 | 内容 | 量级 | 风险 |
|---|---|---|---|
| **① 工具注册** | 把我们**已有的**局部能力包成 agent 可调用的"工具"：区域提亮/压暗、密度增减、量指标、裁一块给用户看… **每个工具要有一份说明书（参数、单位、边界）** | 小（约一天） | 低 |
| **② 自主执行** | **审批流接到界面**、**沙箱与权限边界**、以及 **Windows 上那三个坑**（spawn 子进程弹黑窗 / agent 自己去起浏览器 / ACL 沙箱新建可见控制台） | 大（一周以上） | **高** |

### 【为什么现在不做】

1. **它和我们自己的决策直接冲突**。
   决策 **#44**：*画台不是 agent 项目；LLM 只挑选项、只说人话，不决策、不产参数、不碰执行。*
   **#9**：*运行态 agent 只出 JSON，界面转述它的话。*
   ⇒ **"工具注册"本身就等于把"给工具"这个口子打开** —— 而"不给工具"是我们**故意**选的，
   正是它挡住了这一场遇到的那些坑（agent 编坐标、编参数、自己转多步）。

2. **现在做了也不知道该做什么工具**。
   "该给 agent 哪些工具"完全取决于**用户反复要什么**。而我们**还没有那个数据** ——
   用户目前只是自己在界面里刷几下，**频率和模式都还没看出来**。
   现在做工具化，等于**先造插头再猜要插什么电器**。

3. ★ **它不解决我们当前最大的瓶颈**。
   这一场最大的瓶颈全在**"原图质量"**（用户自己的判断："原图够好就不用后期调"）。
   **agent 再强，也治不了"这张照片里没有眉毛"、"放大到 787px 会糊"。**
   ⇒ 现在的杠杆在**源图体检（乙）**，不在 agent。

4. **收益与代价不成比例**。
   做 ② 要引入沙箱、审批、平台补丁 —— **这些是"基础设施"，投入一次才能用**，
   而我们现在**连第一个需要它的场景都还没出现**。

### 【什么时候该做（触发条件）★ 这是本条的钥匙】

**看到下面任一信号，就该解禁：**

| 信号 | 含义 |
|---|---|
| **用户开始反复描述同一个操作、却不动手**（"你帮我把它弄亮一点" × 很多次） | 说明"说"比"点"更省事 ⇒ 工具化有收益 |
| **用户已经在做"多步组合"**（刷这里 → 再刷那里 → 再量一下 → 再刷） | 说明有**流程**可以自动化，而不是单步操作 |
| **用户能说出抽象需求**（"脸那块整体都亮一点"，而不是"这里刷一下"） | 说明需要"助手拆解成多步" ⇒ 这才是 agent 真正该出场的时候 |
| 有**第二个用户**（朋友）开始用，且他的**用法和你不一样** | 说明需要"通用一点的入口"，而不是你自己记住的固定手法 |

**⚠️ 反过来的判据（别提前做）：**
**如果用户的操作还是"一次一句、看一眼、再一句"，那就还不到时候。**
——那正是我们现在这个形态**最合适**的阶段。

### 【怎么验】（解禁后）

- **① 工具注册**：每个工具必须有**与执行层同源的参数说明书**；
  **参数越界必须拒绝**（不许静默）；**调用后必须独立回读**（不许自证）。← 全部沿用现有四道协议
- **② 自主执行**：**"换掉 dsh 检验"** —— 把 dsh 整个换掉，工具、审批、沙箱**全不算数**，
  我们剩下的（词汇/校验/回读/账）**必须照旧成立**。立的才是资产。
- **③ 平台的三个坑**：分别在 Windows 上实测（弹黑窗 / 自起浏览器 / 沙箱控制台），**不许只按文档假设**。

### 【参考（不搬代码）】

- `参考代码\ai-art-engine-main`：示范了"把 dsh 当基座"能接管到多深（**工具 / 技能 / 人格 / runner / 审批**五层全接管）。
  ⚠️ **GPL-3.0 ⇒ 只读思路，代码与文本不进版本库**（决策 #31）。
- 它同时打了**三个 Windows 补丁**（隐藏子进程控制台 / 禁止启动浏览器 / 沙箱控制台）——
  那三个坑我们**将来一定会遇到**，到时候照这个清单查。
